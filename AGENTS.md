## 2. Polychoric Correlations Policy (November 2026)
- **Policy**: Use polychoric correlations for all analyses of ordinal survey items, including the 7-point past-year frequency items in the activity battery and the 5-point tie items. This covers exploratory factor analysis, reliability (alpha and omega), CFA, ESEM, and any correlation matrix that feeds a measurement model. Use Pearson only for variables that are continuous by design, and state that in the text.
- **Implementation**: `psych::polychoric()` for correlation matrices passed to `fa()`, `principal()`, `omega()`, or `alpha()`. For `lavaan` CFA and ESEM, use `ordered = <items>` with `estimator = "WLSMV"`. Do not pass raw integer item codes to `principal()` or `alpha()` on the Pearson scale.
- **Migration complete (November 2026, see Section 15)**: all three batteries, KMO, alpha, robustness scripts, Figure A1, and the Table A2 count correlations now use polychoric (or polyserial) correlations. No item-level or measurement-level Pearson correlation remains in the main pipeline. The author has decided on the full migration.
- **Sparse top categories**: several activity items have very few responses in category 7 (2 to 9 responses for symphony, movie theater, dance, and similar items). Check category counts before fitting, and run a collapsed-top-category version as a sensitivity check if thresholds are unstable.
- **Verified November 2026**: the polychoric and Pearson varimax solutions give the same 20-item activity assignment, with variance explained of .63 and .59 respectively.

## 12. Reusable Text-Edit Module (`Scripts/docx_text_edits.py`)
Exposes `revise_docx(in_docx, out_docx, full_paragraph_edits=[...], substring_edits=[...])`:
- **Full-paragraph edits**: exact whole-paragraph text match and wholesale replacement — safe for self-contained methods/results paragraphs with uniform run formatting.
- **Substring splices**: run-preserving replacement of just the matched text, needed because this document's entire Discussion section is authored as a single very long `<w:p>` — leaves every other run (and any inline formatting) untouched.
- Both modes collect every `<w:t>` descendant of a paragraph directly (`p.findall(".//w:t", NS)`), **not** one-per-run via `r.find(...)`. A single `<w:r>` run can legally contain more than one `<w:t>` (e.g. split around a `<w:tab/>`); grabbing only the first `<w:t>` per run silently leaves the rest of a multi-`<w:t>` run's *original* text in place. This produced a real stale-duplicate-sentence bug during the oblimin revision — **any future text-edit script in this project (or copied to another project) must collect `<w:t>` this way, not per-run.**
- `revise_docx()` re-registers the standard OOXML namespace prefixes (`w`, `w14`, `r`, `wp`, `a`, `pic`) via `ET.register_namespace()` before serializing — `xml.etree.ElementTree.tostring()` otherwise renames them to auto-generated `ns0:`/`ns1:`/... prefixes, which is valid XML but **pandoc's docx reader fails to parse**, so this must run before any `ET.tostring()` call in this family of scripts.
- `revise_docx(..., require_all=True, validate=True)` (both default `True`) refuses to write `out_docx` at all if any single requested edit fails to match, or if the result fails a `pandoc -t plain` round-trip check — never leave a partially-edited or corrupted `.docx` sitting where a sync driver might upload it.
- For a **new** revision round: either (a) write a new small script that imports `revise_docx` and supplies its own `FULL_PARAGRAPH_EDITS`/`SUBSTRING_EDITS` lists (see `apply_oblimin_text_revisions.py` as the template), or (b) call `docx_text_edits.py` directly as a CLI against a JSON file of edits (`python3 Scripts/docx_text_edits.py <in.docx> <out.docx> <edits.json>` with `{"full_paragraph_edits": [[old, new], ...], "substring_edits": [[old, new], ...]}`). Always run against a **fresh** `drive_download()` immediately before editing, since the author may have made live prose edits since the old-text strings were captured.
- This module is **not** wired into `sync_manuscript.R`'s default flow (image swap only) — text revisions remain a deliberate, reviewed, per-round step, not something that runs automatically on every sync.

**CRITICAL: lavaan 0.7-3 regression pathology onto EFA blocks.** `Scripts/diagnostics/esem_regression_pathology_check.R` + log/rds: with `fixed.x = TRUE`, covariate regressions onto EFA-block factors produce estimates that contradict the item-level associations. Diagnosis: the rotation criterion is evaluated on the model-implied latent covariance of the block, which depends on the regression coefficients, so the optimizer trades rotation simplicity against regression fit; Mplus additionally correlates covariates freely with factors, which lavaan does not under fixed.x = TRUE. Consequence: the demographic-to-network paths in the set-ESEM models (e.g., poli to liberal +.52, to conservative -.15, opposite of the CFA signs and the raw data) are NOT trustworthy. Demographic-to-activity paths in the same models kept plausible signs; network-to-activity paths agreed in direction and significance with the CFA baseline across all specifications, but any covariate-path-onto-EFA-block result in this lavaan version should be treated as suspect.
